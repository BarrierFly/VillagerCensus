# AGENTS.md — Villager Census

Guidance for maintainers and automation working in this repository.

## Project facts

- Client-only Fabric mod (`environment: client`).
- Mod id: `villagercensus`, package root: `net.villagercensus`.
- Multi-version via **Stonecutter**; targets `1.21.11` and `26.3`.
- Depends on **Fabric API** and **MaLiLib (sakura-ryoko fork)**.
- Uses official Mojang mappings (layered offline mappings for obfuscated versions,
  no-remap for 26.1+).

## Build

```bash
./gradlew build                 # builds every registered version
./gradlew clean build
./gradlew stonecutterSwitch     # switch the active version (see stonecutter.gradle.kts)
```

Per-version artifacts: `versions/<mc>/build/libs/villagercensus-<modver>+<mc>.jar`.

There is currently **no automated test task** (no test sources). Verify changes by building
all versions and by in-game manual testing.

## Stonecutter rules — IMPORTANT

Stonecutter's on-disk shared source in `src/main/java` **must always be valid for the active
version** (`stonecutter.gradle.kts` currently `26.3`). Non-active versions are generated by
stripping/keeping conditional blocks.

Comment syntax used in this repo:

```java
//? if >= 26.1 {
// active when version >= 26.1
//?} else {
/*// inactive branch, commented out
*///?}
```

Key version boundaries used:

- `< 26.1` vs `>= 26.1`
  - `MultiPlayerGameMode.interact` signature (`EntityHitResult` parameter added).
  - `IRenderer` callback (`onRenderGameOverlayPostAdvanced` vs `onExtractGuiOverlayPost`)
    and registration (`registerGameOverlayRenderer` vs `registerInGameGuiRenderer`).
  - Fabric API client commands (`ClientCommandManager` vs `ClientCommands`) — avoided by
    using Brigadier directly.
- `< 26.2` vs `>= 26.2`: `Minecraft.screen` field vs `mc.gui.screen()`.
- `ResourceKey.location()` is **`ResourceKey.identifier()`** in these mappings.
- `1.20.6+`: `MerchantOffer` uses `ItemCost` (not relevant to the shared code, which reads
  `getBaseCostA()`/`getCostB()`/`getResult()`).

When adding version-specific code, write the **active version's branch uncommented** and put
the other branch in the `/* ... */` block. Then build all versions.

## Architecture

```
command/    Fabric client commands
census/     session state machine, records, undo stack, interaction manager
trade/      trade category catalog + matching
data/       report writer, draft storage, world-id/filename helpers
mixin/      interact / offers / openScreen hooks
render/     HUD (malilib IRenderer)
config/     malilib config options and hotkeys
event/      malilib init, keybind callbacks, world load listener
util/       version shims and name formatting
```

Interaction contract (do not break):

- `MultiPlayerGameMode.interact` only **registers** a pending target; it never cancels the
  vanilla interaction.
- `handleMerchantOffers` **never calls `ci.cancel()`** (offers-hud compatibility).
- `handleOpenScreen` cancels only when a matching pending target exists and the type is
  `MenuType.MERCHANT`.
- **Threading:** `handleMerchantOffers` / `handleOpenScreen` run on the Netty network thread.
  They must only touch thread-safe state (the offers queue, `volatile` pending/tick fields)
  and must never call malilib message/render helpers or mutate entities there. All record
  building, messaging and entity access happens in `CensusManager.onClientTick` (client
  thread), which drains the offers queue.

## Code style

- Match the surrounding code: 4-space indent, Allman braces, explicit types where the
  project already uses them.
- Do **not** add comments unless they explain non-obvious version/mapping workarounds.
- Keep Minecraft-facing calls behind small helpers (`util/Compat`, `census/CensusManager`)
  so version drift stays contained.
- Avoid literal `%` in translation strings (malilib formats with `String.format`); use `%s`.

## Resources

- `assets/villagercensus/lang/{en_us,zh_cn}.json` — follow game language for messages and
  reports. Config keys follow malilib's `ConfigBase.apply(prefix)` scheme:
  `<prefix>.prettyName.<name>`, `.comment.<name>`, `.name.<name>`.
- `villagercensus/trade_categories.json` — semantic trade category catalog loaded at runtime.
  It was generated from the decompiled vanilla trade table in the `guardian` repository
  (branch `mojmap/vineflower`):
  - 1.21.11 commit: `192e7132b4` → `src/main/java/net/minecraft/world/entity/npc/villager/VillagerTrades.java`
  - 26.3 commit: `d5822ca2a1` → `src/main/java/net/minecraft/world/item/trading/VillagerTrades.java`
  - 1.21.11 uses explicit `ItemListing` constructors; 26.3 uses `VillagerTrade.builder(...)`
    with `ColorCollection` loops and `create*` helper methods, and assigns trades to
    professions through `data/minecraft/tags/villager_trade/<profession>/level_*.json`
    (recursively including `common_smith`).
  - Both versions are fully parsed and merged (303 categories, 0 unresolved). Regenerate with
    the parser scripts (see commit history) via `git -C <guardian> show <commit>:<path>`.

## Commits

- Only commit when explicitly asked.
- Conventional-ish, imperative subject lines; describe behavior changes and version scope.
- Do not commit build outputs, the `run/` directory, or IDE files (see `.gitignore`).
